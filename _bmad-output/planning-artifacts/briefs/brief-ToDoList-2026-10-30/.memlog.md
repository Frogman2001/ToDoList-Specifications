- (decision) Purpose: personal hobby project for the author, but built professionally with focus on engineering quality and maintainability.
- (decision) Intentionally limited featureset; usability via simplicity. Explicit goal: avoid Trello's drift into complexity.
- (decision) Form factor: web app AND mobile app (like Trello).
- (decision) Core concept: date focus - Today / Tomorrow / Future - with easy push-out-to-future.
- (decision) Opening the app must make two things easy: add item to current list, view current list.
- (decision) Item fields: description, state (not started/in progress/done), detail, due date, address.
- (decision) No hard cap on functionality; solo developer self-manages scope creep (user rejected cap/never-list).
- (change) Removed address field: addresses live on calendar entries (separate, unconnected app). Item fields now: description, state, detail, due date.
- (decision) Date model: items dated today or earlier (incl. overdue) appear on Today list. Reschedule actions: set specific date, push to tomorrow, next week, next month.
- (decision) Web + mobile because: web for full keyboard, mobile for on-the-go. Build TWO front ends against ONE back end as a deliberate hobby challenge.
- (decision) Problem: all of Trello's features annoy the user. Secondary goal: needs a project application to build (learning/engineering vehicle).
- (assumption) Today/Tomorrow/Future are computed views from due date, not manual buckets (inferred from user's date model; confirm).
- (decision) Simple features/UX, but implementation follows common coding+testing practices; architecture complexity from two front ends is accepted. Learning/engineering goals sit alongside usability.
- (decision) No documented feature cap or guardrail; user trusts self to remove features that annoy them (reaffirmed).
- (decision) Lists are NOT first-class; they are dynamic views over dated items. Views: today, a specific date, this week, next week, another week (week view = all items dated within that week). Date required in data, defaults to today if user omits.
- (decision) Done items stay on the list; 'hide completed' toggle; user can scroll back through past dates to see what was completed on that day.
- (decision) Hosting: Azure intended (not required). Auth: SSO via Google, Facebook, maybe others. Audience: author, family, other random people - multi-user.
- (decision) Success criteria: phase 1 features (defined in this brief) complete and deployed to production. Building/maintaining the app is itself the hobby + professional development.
- (assumption) OPEN: 'today or earlier shows on Today' vs 'scroll back to see completed on past dates' - done past-dated items must not clutter Today; needs rule.
- (assumption) OPEN: 'completed on that day' - is it due date or actual completion date? Model currently has only due date.
- (assumption) OPEN: multi-user scope implications (data privacy, account deletion, hosting cost, support) not yet discussed; phase 1 undefined.
- (decision) Today view shows every not-started/in-progress item dated today or earlier. Done items do not roll forward; they stay on their own date. Date field never changes unless user edits it. Principle: data is stored plainly, display interprets it.
- (decision) Store two dates per item: due date and completed date. Usually equal but distinct concepts. Display is driven by due date; completed date is informational for now.
- (change) Item fields now: description, state, detail, due date, completed date (set when state becomes done).
- (decision) Phase 1 auth: Google only (startup mindset: build only what's needed). Facebook/others deferred.
- (decision) Not publicized until admin tools exist. Positioned as a hobby; imperfection accepted early.
- (decision) Phased, non-waterfall: build phase 1 scope (as outlined in brief), learn what works, then plan later phases. User doesn't have all answers up front.
- (decision) Phase 1 scope confirmed at high level: Google SSO, add item, views (today/date/week), change state, edit detail, reschedule (tomorrow/next week/next month/pick date), hide completed, web + mobile front ends, deployed to production.
- (decision) Differentiators confirmed: no lists (everything is a dated item), overdue items roll into Today until done, one-action rescheduling.
- (decision) Vision: family and a few other people use it. No enterprise/scale design up front; if it explodes, rebuild then ('good problem to have').
- (decision) Phase 1: delete items with standard user confirmation; NO offline mode (too much complexity); NO sharing between users (each user sees only own items).
- (decision) Delivery model: sequential bounded projects (like sprints/quarterly projects), each with a defined end; hobby continues across many projects. Follow typical BMAD flow per project; this brief covers project 1 only. Not waterfall to a final end state.
- (change) Terminology: 'phase 1' replaced by 'project 1' in brief to match the sequential-projects model.
- (event) Finalize: audit approved by user; addendum written; structure+prose review applied (addendum date-model section condensed to avoid duplicating brief; 'day' -> 'date' wording). Brief status set to complete.
- (change) Synced brief with PRD: added reorder-by-dragging (scope + solution), ordering rule, web/mobile parity.
- (change) Architecture coaching adopted Azure as the host, a React web app, and a .NET MAUI Android app, with Cosmos DB. Brief Technical Direction updated. Item document shape is still open in architecture.
