- (decision) User expects multiple UX flavors for different form factors (web and Android known; others TBD).
- (decision) From PRD, UX-owned questions: drag that reorders AND reschedules (drop targets); week view layout (vertical list with dividers vs one column per day by screen size); hide-completed persistence; per-day add control; quick add as simple as a Post-it, add control stays ready after each add.
- (decision) Working mode: Coaching.
- (decision) Layout: responsive; number of day columns driven by available space. Rough intent: phone portrait = 1 column (one day or stacked days); phone landscape = 2 days; small tablet = 2-3; larger browser widths accommodate more. Each day is a box. On narrow screens, week view scrolls horizontally.
- (decision) Mobile navigation: swipe left/right between list and 'add new', like two tabs. In week view with horizontal scroll, 'add new' is the leftmost column.
- (decision) Mobile move gestures: grab one or more items and swipe right to move to tomorrow; alternative: tap an item then choose tomorrow / next week / next month.
- (decision) Mobile state gestures: maybe double-tap to advance state; plus a tap option to pick a specific state (e.g. back to in progress from done).
- (assumption) OPEN: gesture conflicts on mobile (tab swipe, week horizontal scroll, item swipe-right, drag reorder, multi-select); add-new date in week view vs per-day add control (PRD FR-3); default screen on open; multi-item (bulk) move is new vs PRD FR-11; web interactions not yet discussed.
- (decision) Mobile columns: week mode = 8 columns (Add new leftmost + 7 days); day mode = 2 columns (Add new + the day). Horizontal scroll navigates between them. Single day = one column.
- (decision) Mobile opens on the Add new screen: a very clean screen that does not show other items. Also a per-day add button that opens a small popup in the context of the list. Two ways to add on mobile.
- (decision) Mobile moving: tap-and-hold to select ONE item, then swipe. One item only on mobile (multi-select too complicated). Double-tap advances state (mobile only); tap option to pick a specific state.
- (decision) Web: opens on week view; NO swipe/add screen; per-day add button opens popup; click-hold-drag to move; Ctrl+click for multiple; multi-item action is MOVE only; other changes one by one.
- (decision) Web keyboard shortcuts proposed by user: Ctrl+N new task; Enter save; arrows move between fields on new item; list: Up/Down move selection, Left/Right previous/next day; Ctrl+Up/Down multi-select; Ctrl+Left/Right move selected item(s) one day. User asked for more ideas.
- (assumption) OPEN: swipe direction to reach Add new; Ctrl+N is reserved by browsers; Ctrl+Up/Down reserved for multi-select so reorder needs another chord; mobile reorder gesture after tap-hold; mobile list default day; Add new default date; user item 8 was blank.
- (decision) Swipe direction: finger moves right to reveal the left column (Add new), like dragging a slider over.
- (decision) Mobile swipe modes: no item picked up -> swipe scrolls to next column; item picked up (tap-hold) -> swipe moves that item to the next day.
- (decision) Phone day mode default: one day plus Add new column; move between days by scrolling.
- (decision) Phone Add new screen has a date picker, defaulting to today, or to the day it was reached from. Screen stays open (cleared) after each add for repeat adds.
- (decision) Web shortcuts: Alt+N new task (Ctrl+N is browser-reserved); Alt+Up/Down move item up/down within its day. Accepted all suggested extras: Esc close/clear selection, Delete (with confirm), Space/letter keys for state, single-letter reschedule keys, T today, ? shortcut cheat sheet. Exact letters still to be assigned.
- (assumption) Assumed: picked-up item swiped left moves to previous day; picked-up item can be dragged up/down to reorder on mobile; confirm. Proposed keys: Space advance state, 1/2/3 set state, D tomorrow, W next week, M next month, T today, ? help.

- (decision) Wireframes approved: simple is good.
- (decision) Web theming: multiple looks and feels by swapping CSS. Design the default look now; architecture decides how swapping is supported.
- (decision) Look and feel direction: unornamented, straightforward app.
- (decision) Theming: project 1 builds an app that COULD have themes later; swap mechanism is an architecture task. First theme = dark. Font: normal sans serif, expected to change per theme.
- (decision) Style: simple functional shapes; areas defined by a line and/or subtle background difference; buttons/links use clear descriptive text (e.g. 'Add'); avoid icons unless truly best; no icon-next-to-text clutter. Shadows/gradients/borders: use spacing, a line, or a border to distinguish parts without being busy.
- (decision) Color: simple palette, little color; green suggested ('getting things done') but user flexible; color must NOT indicate state. State uses iconography: to do / in progress / done, ideas = checkbox vs filled/checked box, or handwritten dash with dot for in progress and vertical line for done; designer to propose.
- (decision) Done items: checked/filled box AND greyed out so open items carry more weight.
- (decision) Density: roomy over packed (finger-sized targets on phone). Spacing dynamic: once column count is chosen, columns expand to fill available width.
- (decision) Usability features wanted: calendar date picker; typed dates with digits only (punctuation auto-added) or with slashes or dashes; sensible tab order; NO 'may I help you' popups/tours. Animation only with purpose (e.g. showing an item moving; light animation on popup/dropdown to explain why it appeared).
- (decision) Delight is in usability: every action logical, app fluid, little thinking required.
